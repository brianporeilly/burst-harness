MCP servers

Servers a session's or task's agent can connect to, over HTTPS. New sessions and tasks get the ones on by default, and their forms show every one here to pick from. A server's key goes in the Credentials: NAME_API_KEY for a bearer token, or NAME_BASIC_AUTH as user:secret (not encoded) for a server that takes Basic auth, such as an Atlassian personal API token. The gateway adds it. Those from the configuration (HARNESS_MCP) can be turned off by default, or replaced by one of the same name.

Runners

Hosts of your own that tasks and jobs can run on, over SSH. A podman or docker runner runs each one in a container on that host, with its gateway, as here; a plain host (ssh://) gets a directory per run, with no gateway, so its network is open and the agent's credentials are written there for the run: give it a machine of its own that you reset. New tasks run on the default runner unless they pick another; a job picks one in its job.toml (runner = "NAME"). Those from the configuration (HARNESS_RUNNERS) can be replaced by one of the same name.

Webhooks

A forge can tell the orchestrator when a PR is merged or a branch is pushed, so a task carries on and a job repo syncs straight away rather than at the next look (every few minutes, which goes on anyway). In the repo's settings, add a webhook to the address below, content type application/json, with the secret set here as the credential named, for Pull request and Push events. What a delivery says is only a hint: the orchestrator looks for itself.

Job repos

Git repos of jobs, beside the orchestrator's job directories. Each is synced every few minutes, or now with Sync, and its jobs are read from one commit at a time; a run records the commit it ran from. Nothing is written back. A private repo is read with the credential named (JOBS_GIT_TOKEN unless you name another): a token that can only read it. Those from the configuration (ORCHESTRATOR_JOB_REPOS) are changed there.
